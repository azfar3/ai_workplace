# Duplicate WhatsApp replies and echo loops

## Confirmed code defects

1. A custom gateway payload without `message_id` previously received a random
   UUID on every delivery. Gateway retries therefore became new AI requests.
2. Async workers used get-then-process-then-set for their completion cache.
   Concurrent jobs could both call tools, generate answers and send replies.
3. An outbound-log check compared the original inbound ID with a provider-generated
   outbound ID. Those IDs differ, so this was not a valid duplicate-delivery guard.
4. The legacy webhook URL ran a separate synchronous implementation.
5. Echo filtering recognized an older AI footer but missed the current
   `🤖 This response was generated by AI.` footer and generic closing. Some
   forwarded bot messages could consequently be treated as new user questions.

These defects are confirmed from the repository. Which path produced any
particular live duplicate still requires the corresponding inbound/outbound logs.

## Changes

- Webhook retries first check committed inbound logs, then acquire one atomic
  Redis SET NX EX ingress lease. Competing deliveries before the first log commits
  receive HTTP 503 so the provider can retry; committed duplicates receive 200.
- Queued and synchronous text processing both claim the inbound log under a
  database row lock and commit its Processing State before executing tools/AI.
- Sending is persisted before contacting the provider. Claimed/Sending/Sent/Failed
  work is never automatically replayed. Before migration, the fallback uses an
  atomic seven-day Redis worker claim.
- Outbound logs record Reply to Inbound Message ID for diagnostics. They no longer
  try to infer a response relationship by matching unrelated provider IDs.
- Enqueueing is explicitly after commit, and the legacy URLs delegate to the
  canonical implementation. The worker is no longer a guest-callable HTTP method.
- Original gateway IDs, including `key.id`, are preserved. Outgoing flags include
  boolean/string values and nested Baileys flags. Current bot-footer and closing
  echoes are ignored.

## Gateway contract

Prefer forwarding the original WhatsApp event like this:

```json
{
  "number": "923001234567",
  "message": "Tell me about MicroMerger",
  "message_id": "ORIGINAL-WHATSAPP-MESSAGE-ID",
  "fromMe": false,
  "timestamp": 1793610000
}
```

`id`, `messageId`, or `key.id` can substitute for `message_id`. If the gateway
cannot supply an ID, the original stable event timestamp permits a deterministic
fallback fingerprint. It must not be replaced with the current delivery time on
retries. Payloads without both ID and original timestamp are logged as ParseError
and acknowledged without AI processing, avoiding an endless retry loop. This is
an intentional compatibility change: update the gateway before rollout if it
currently sends only `number` and `message`.

Two messages with different real provider IDs are distinct, even if their text
is identical. This prevents legitimate repeated questions or menu choices from
being incorrectly suppressed by text-based deduplication.

## Deployment and verification

1. Verify the gateway includes an original event ID and outgoing flag. Its outbound
   send URL must point to its send API, not back to this inbound webhook.
2. Run `bench --site <site-name> migrate`. The new message-log fields and a patch
   mark previously finalized inbound logs so old queued jobs cannot replay them.
3. Restart web and all background workers so neither legacy code nor an old
   already-running worker continues to process messages.
4. Send one question; confirm one inbound ID has one primary reply. Redeliver the
   exact same payload concurrently: no additional AI/tool execution should occur.
5. Send the same text with a new event ID: it should be answered normally. Deliver
   an outgoing echo: it should be acknowledged without an AI answer.

The generic closing is still a separately configured follow-up when no contextual
question replaces it. That is independent of duplicate full-answer processing.

Claimed/Sending records after a worker crash are deliberately not reset on a timer:
ERP writes or provider delivery may already have completed. Inspect the provider
and linked logs before any manual recovery. Exactly-once external delivery cannot
be guaranteed across an uncertain network failure without provider idempotency.

Local regressions:

```sh
python3 -m unittest ai_workplace.tests.test_whatsapp_idempotency -v
```

These tests use fake site/cache/database adapters. Live Redis/Frappe concurrency
and provider webhook delivery still require the configured test site.
