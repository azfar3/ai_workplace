1. Executive Summary
MicroMerger requires a practical employee self-service platform that removes avoidable dependency on HR, operations and administrative staff for routine questions, status checks and data entry. The proposed AI Workplace will use WhatsApp as the primary employee-facing interface because it is familiar to field staff, consultants and office employees, including users who do not regularly use the ERP portal.
The solution will be developed as a native ERPNext/Frappe custom application. It will reuse existing MicroMerger ERP data, permissions, workflows and the existing policy module. It will not create a second HR or policy system. Incoming WhatsApp messages will be matched to the employee's or consultant's registered personal or official mobile number in ERP and then routed to deterministic ERP services or, only where needed, an AI/RAG service.
The MVP is deliberately pull-based: the system responds when the user initiates a conversation. It will not proactively send reminders or notifications in the first release. This reduces message cost, avoids unnecessary interruptions and simplifies consent/template management. Proactive notifications are planned for a later phase.
MVP outcome: A staff member messages the official number, is identified automatically, sees a role-specific menu, asks project-relevant policy questions, checks HR data, submits eligible transactions, uses consultant functions where applicable, and obtains/records travel information without opening ERPNext.
2. Background and Business Problem
MicroMerger manages a mixed workforce across multiple projects. Policies may be organization-wide, project-specific or employee-specific. The current ERP already models users, projects, reporting relationships and policy applicability, but adoption of the full web interface is uneven. Some field staff have limited computer literacy, some consultants do not routinely use the ERP portal, and many users prefer mobile messaging for quick operational actions.
High volume of repetitive HR and policy questions.
Users call/message individuals instead of using documented policies or ERP self-service.
Consultant timesheets, deliverables and invoices may require manual follow-up or re-entry.
Project-specific policies can be misapplied when staff receive a general answer.
Travel information and complaints are fragmented across different people/channels.
ERP features are under-used by staff who are less comfortable with conventional web interfaces.
Manual follow-up reduces HR/operations time available for higher-value work.

8. Business Process Flows
8.1 Generic User-Initiated Conversation
User messages the official WhatsApp number.
Meta sends the inbound event to the ERPNext webhook.
Webhook signature/payload are validated and message ID checked for replay.
Sender is normalized to E.164 and matched to active ERP records.
Unknown or ambiguous identity is denied without revealing employee data.
System loads ERP context: employee/consultant type, projects, roles, reporting context and allowed services.
Router classifies navigation, deterministic ERP action, knowledge/RAG question or unsupported request.
Selected service executes under server-side authorization.
Inbound/outbound messages, action, latency and errors are logged.
8.2 Policy Question
Resolve identity and authorized policy scope.
Detect language and normalize query.
Build metadata filter from existing policy applicability.
Search only permitted chunks using hybrid retrieval.
Return safe 'not confirmed in your applicable policies' when evidence is weak.
Otherwise synthesize a concise answer in user's language with policy/version/page or section.
Log retrieved policy/chunk IDs and scores.
8.3 Leave Application
User selects My HR > Leave > Apply Leave or asks naturally.
System loads eligible leave types and entitlement from existing ERP logic.
User chooses type/dates and provides reason.
System shows a confirmation summary.
On confirmation, app invokes existing ERP validation/workflow logic.
Existing supervisor/workflow email approval remains unchanged.
WhatsApp returns ERP reference and current status.
8.4 Travel Journey Update
User opens My Travel or says 'start travel'.
System finds approved/current travel record in configurable date/time tolerance.
If multiple records match, user selects one.
User shares WhatsApp location; system stores coordinates, timestamp and Meta message ID.
Progress updates append to the same travel log.
Issue/complaint captures category, description, severity and optional evidence, linked to active trip/driver/vehicle when unique.

13. Identity, Authentication and Authorization
13.1 Phone-Based Identity
Every inbound message is resolved from the WhatsApp sender ID/phone number. Both personal and official mobile fields may be accepted. Normalize to E.164 before comparison.
ID
Rule
IR-01
Strip spaces/punctuation; normalize local Pakistan mobile format to E.164 and support international values.
IR-02
Match only active/eligible ERP employment/engagement records.
IR-03
If personal and official numbers point to the same person, it is a valid identity.
IR-04
If a number points to multiple different people, fail closed and create data-quality alert.
IR-05
No match -> generic registration/support response; no protected menu.
IR-06
Resolve identity on every inbound protected request; conversation state is not the sole security control.
13.2 Authorization Model
The conversation layer must not expose generic ERP CRUD to AI. Each feature has a dedicated business service that receives a UserContext and verifies the specific operation. Where portal logic already performs authorization, reuse it.
UserContext {  wa_id,  normalized_phone,  erp_user,  employee_id?,  consultant_id?,  person_type,  active_projects[],  roles[],  reporting_context,  allowed_services[],  preferred_language}
Avoid `ignore_permissions=True` for protected business data. It may be used only for technical logs where appropriate. For high-risk features such as salary documents or master-data changes, keep them out of MVP or require future step-up authentication.
14. WhatsApp Conversation and Menu Design
14.1 Interaction Strategy
Use menu-first plus free text at any point. Menu navigation avoids unnecessary AI calls and is easier for less technical staff. Free text preserves convenience.
User Context
Example Main Menu
Employee
1. My HR2. Policies & Help3. My Travel4. My Tasks (future)5. Help / Change Language
Consultant
1. My Engagement2. Timesheet / Deliverables3. Invoice / Status (if enabled)4. Policies & Help5. My Travel6. Help / Language
Employee + Manager
Employee menu plus authorized team functions when feature is enabled.
Unknown Number
No protected menu; registration/support message only.
Use reply buttons for confirmations/short choices and list messages for larger menus. Current Meta Cloud API documentation allows up to three reply buttons and up to ten list rows across sections; the implementation should validate current limits at deployment.
14.2 Language
Detect first-message language and offer English / Urdu / Roman Urdu.
Persist preferred language on WhatsApp Identity and allow change anytime.
ERP labels remain internal English; channel layer provides localized labels.
Keep official policy/leave/status names in English in brackets when useful.
Roman Urdu intent should tolerate spelling variation.
14.3 Conversation State
Use a short-lived state machine for multi-step actions: intent, selected record, expected input, draft payload and expiry. 'Cancel' or a new main-menu command resets the flow. State-changing actions require final confirmation.
15. AI, RAG and Knowledge Architecture
AI is constrained. Policy answers must be grounded in authorized content. ERP actions use AI only to map free text into a fixed intent; deterministic server code executes the action.

15.2 Ingestion Pipeline
Trigger on approved policy publish/replace/version change.
Fetch PDF from existing policy record.
Extract embedded text; use OCR only if extraction fails/image-only.
Clean repeated headers/footers while preserving page/section mapping.
Chunk by heading/paragraph, target ~600-900 tokens and modest overlap.
Attach metadata: policy ID/title/version/effective date/scope/page/section/status.
Generate BGE-M3 embeddings and upsert into vector index.
Store checksum/index version in ERP; invalidate old chunks/caches.
15.3 Retrieval and Answer Pipeline
1. Resolve UserContext2. Build authorized policy filter from ERP3. Detect/normalize language4. Hybrid retrieve semantic + lexical5. Optional re-rank6. Reject if evidence score is below threshold7. Send only authorized top chunks to LLM8. Generate concise answer in user's language9. Attach policy title/version/page or section10. Log sources, scores and answer
